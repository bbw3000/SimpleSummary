## 如何使用

本插件易于使用，界面简单友好。插件右上角可切换多语言以及明/暗主题。
插件入口在消息输入框左侧的魔法棒菜单中。你也可以使用`/sp`指令打开插件。

* [ ] **Step. 1 配置API**
  
  - 默认支持openai兼容格式的Custom接入，以适配许多第三方API（比如openrouter、SiliconFlow）。对于高级用户，Custom接入点还可以使用自定义参数。
  - 同时支持openAI、Anthropic、GoogleAIStudio三种直连/反代接入点。
    你只需要填写BaseURL、API Key，然后拉取模型、选择你要使用的模型（或者选择手动输入）。
    （细节设计：当使用Anthropic、GoogleAIStudio接入方式时，会先使用openai格式拉取模型列表，如果无返回，则使用ST内置的列表。这个设计方便一些比如NewAPI中转）
* [ ] **Step. 2  开始摘要**
  
  - 回到首页，选定一个需要摘要的范围。确定摘要范围（比如0~30）后，你可以直接点击生成摘要按钮，插件便会开始工作了。（默认开启了流式）你可以看到摘要在输出。当输出完毕时，你可以直接保存，或者检查修改后再保存。在开始摘要前，你也可以点击请求预览按钮，查看真实发送给LLM的完整请求信息。（其中包含LLM参数、摘要的提示词、你选定范围的聊天记录）
  - **注意，范围的起始消息数是不可选的。** 这是我的设计，以防起始消息数和之前已摘要的消息范围有重叠。起始消息数是根据最后一条被设定为hide的消息来确定的。如果这是你第一次使用本插件，而起始消息数字不是0，你可能使用过其他摘要插件或者手动hide过消息。你可以打开自动对齐摘要（Auto-Repair Summary）功能并刷新页面，插件会自动帮你清除所有未摘要消息的hide状态（对初次使用，就是unhide全部消息）。
* [ ] **Step. 3  没了**
    - 摘要默认由插件自动注入到聊天记录的 @depth 999 位置，以一条system message存在。你可以从ST 预设的ChatHistory里看到一条‘Name: chatHistory-1, Role: system, Tokens: xxxx’。如果你希望自己控制注入位置，可以在插件的设置页关闭插件注入，自行使用 `{{SPSummaries}}` 宏来注入到你想要的位置。比如，你可以放在ST预设里，或者世界书，或者作者注释。
  - 插件还支持正则预处理。如果你玩的是一些前端卡，可以使用正则过滤掉消息中的一些不需要摘要的内容（比如角色/NPC状态之类）

## 为什么用这个插件？

用过许多其他的摘要插件后，总觉得找不到合适自己的，于是我决定自己做一个。
许多插件提供RAG、表格，还有的使用特定的格式。
但实际效果往往难以如意。为何？主要两个原因：

- **LLM没有时间状态** 许多人都知道，LLM可能甚至会做错9.8-9.11这样的数学题，所以不要太指望LLM一定能准确理解9月11日发生的事，是在9月8日之后的事情。因此，即便你给每件事发生的时间都做了时间标记，只要顺序不对，LLM依然可能错误理解。而使用RAG技术插入信息条目更是可能带来灾难性的时间/事件乱序后果：你甚至并不一定能及时发现后果，因为LLM并不会直白的写出它的理解，而是可能包含在隐藏的文字下、逻辑中，直到可能许多条消息之后你才在某个细节忽然意识到，糟糕，LLM早就对事件理解出现了偏差。
-  **LLM天然倾向顺序事件排列** 尽管很早期的一些旧型号会可能在超长上下文时搞错，但目前的LLM大多表现良好。顺序排列的事件context是LLM最易理解的第一方式，而LLM都是使用人类自然语言来训练、理解故事剧情的，这也意味着最普通直白的摘要方式是LLM最能准确接受的。

于是，就像插件的名字一样，它就只简单做一件事——把超长上文压实成自然语言摘要。

## 其他事

- 插件注册了几个ST宏，你可以自行用来设计摘要提示词，分别是：
  
  - `{{chatLang}}` : 根据已有摘要/当前选定待摘要消息中的用户消息来判定，输出纯文本语言占比列表，按占比从高到低逐行输出，例如 `zh-CN: 78%, en: 20%`
  - `{{SPSummaries}}` : 已有的全部摘要内容。
  - `{{latestSegment}}` : 仅最新一段的 `summaryText`，长度比 `{{SPSummaries}}` 显著小。
  - `{{chatLog}}` : 选定范围的，已预处理过的聊天消息。
